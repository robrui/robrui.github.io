PYTHONOPTIMIZE=2 Crashing C Extensions

coreforecast#131  ·  February 2025  ·  ~10 min read
TL;DR: Nixtla's coreforecast library crashed with a segmentation fault when Python ran with -OO (PYTHONOPTIMIZE=2). Root cause: assert __init__.__doc__ was used as a guard before calling .format() on it — but -OO strips all __doc__ strings, making them None. The fix: replace assert-based guarding with an explicit if __init__.__doc__: check.

1. Background: Python's -O and -OO Flags

Python offers two optimization levels beyond the default:

Flag Effect
-O (level 1) Removes assert statements. Sets __debug__ = False.
-OO (level 2) Does everything -O does, plus strips __doc__ strings.

These flags are commonly used in production deployments to reduce memory footprint and improve startup time. The CPython compiler simply omits docstrings from the bytecode when -OO is active: 

# With -OO: this entire string literal is compiled to a NOP and eliminated
def my_function():
    """This docstring disappears under -OO, becoming None."""
    pass

# For class __init__:
class MyClass:
    def __init__(self):
        """This also becomes None under -OO."""
        pass

# Attempting .format() on None: AttributeError!
print(MyClass.__init__.__doc__)  # None under -OO
MyClass.__init__.__doc__.format(x=42)  # ❌ AttributeError

Most production Python code accounts for this. But the coreforecast library had a subtle pattern that didn't.

2. The Bug: assert-Guarded Docstring Formatting

The pattern in coreforecast looked something like this: 

class SomeModel:
    def __init__(self, param1, param2):
        """Initialize model.
        
        Parameters
        ----------
        param1 : {type1}
            Description of param1.
        param2 : {type2}
            Description of param2.
        """
        # ... setup code ...

# After class definition, dynamically update docstring with types
assert __init__.__doc__  # Guard
__init__.__doc__ = __init__.__doc__.format(type1="float", type2="int")

The developer used assert __init__.__doc__ as a guard to ensure the docstring exists before calling .format() on it. Under normal Python (no optimization flags), this works perfectly:

  • assert __init__.__doc__ passes ✓
  • .format() succeeds ✓
  • Docstring is populated with actual types ✓

But under -OO:

  1. __init__.__doc__ is None (stripped by compiler)
  2. The assert statement is removed entirely by the compiler
  3. .format() is called on None → AttributeError
  4. If this happens at module import time, the import fails → cascade of failures

In coreforecast's case, the crash was even more severe. The docstring formatting was part of a C extension's module initialization, and the AttributeError propagated through the C API boundary, causing a segmentation fault rather than a clean Python exception.

3. The Fix: Proper Runtime Guard

The fix is to replace the assert guard with an explicit runtime check that survives optimization: 

# Before: ❌ assert gets removed under -O/-OO
assert __init__.__doc__
__init__.__doc__ = __init__.__doc__.format(type1="float", type2="int")

# After: ✅ Runtime guard -OO can't remove
if __init__.__doc__:
    __init__.__doc__ = __init__.__doc__.format(type1="float", type2="int")

The semantic difference is subtle but critical:

  • assert is a debugging aid. The compiler is allowed to remove it under -O.
  • if is control flow. The compiler can never remove it.

Never Use assert for Control Flow

This is a well-known Python gotcha, but it keeps resurfacing. The Python documentation is explicit:

"Assertions should not be used for data validation or control flow. They are debugging aids that can be disabled at runtime." — Python Documentation, assert statement

The reason is exactly this scenario: production deployments often run with -O or -OO for performance, and any logic hidden behind assert silently disappears.

4. Reproducing the Bug

# Run Python with -OO flag
python3 -OO -c "
import coreforecast
# Segfault or ImportError!
"
# Minimal reproduction
class Model:
    def __init__(self):
        """Init with {param_type} support."""

# This works normally
try:
    assert Model.__init__.__doc__
    Model.__init__.__doc__ = Model.__init__.__doc__.format(param_type="float")
    print(Model.__init__.__doc__)
except (AttributeError, AssertionError) as e:
    print(f'Error: {e}')

# Under -OO, assert is removed, __doc__ is None:
#   → AttributeError: 'NoneType' object has no attribute 'format'
# Fixed version:
if Model.__init__.__doc__:
    Model.__init__.__doc__ = Model.__init__.__doc__.format(param_type="float")

5. Why This Matters

This bug is a textbook example of why assert is not control flow. For production Python deployments:

Defensive Patterns

  • Always use if / else for runtime guards, never assert
  • Test your code with python3 -OO -c "import your_package"
  • CI pipelines should test the -OO path, especially for C extensions

C Extension Safety

C extensions are particularly vulnerable because:

  • A Python exception in module init may not be safely caught by C code
  • The GIL state may be inconsistent, leading to segfaults
  • Memory allocated before the exception may not be freed

Libraries like NumPy, SciPy, and pandas have all had similar bugs over the years. The fix is always the same: move critical guards from assert to if.
